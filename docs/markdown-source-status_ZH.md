# 旧 Windows Markdown 来源状态

2026-09-28：用户要求先从 SelfIndex 中停用旧 Markdown 来源，但不删除任何具体 `.md` 文件或库内原文。

## 来源与范围

- 库中来源：`markdown` / `note_file`，单一旧 Windows 同步目录（本机路径不公开；数据库中反斜线曾被重复保存）。
- 旧归档 126 篇，均为 `.md`；停用前有 1,110 个当前搜索单元。
- Mac 上有一个可能对应的 Obsidian 同步目录（本机路径不公开）。该目录现有约 594 个 `.md`，仅 113 个与旧归档的相对路径相同，另 13 个旧路径未找到；**未比对正文，也未建立新旧路径映射**。

## 已执行的软停用

在唯一服务停机、新备份完成哈希及隔离恢复验证后，仅把准确匹配旧根路径的 126 行 `raw_documents.is_active` 设为 0，同时递增编辑版本。原文、修订历史和 Mac 上的文件均未删除或改写。1,110 个搜索向量已清理，SQL 当前有效单元与 Chroma 向量均为 15,410；全量索引对账无缺失、孤儿、正文或元数据差异。原文哈希与备份一致，原始文档及修订总数未变。

重启后 `/api/v1/status` 为 `index.state=ready`，三种待处理队列均为 0；停用文档详情返回 404，普通搜索正常且不返回 `markdown` 来源。

## 日后恢复

停用不是删除，但旧 Windows 路径尚未映射到 Mac。不要直接对 Mac 目录运行真实同步：它包含大量未入库文件与已移动的旧路径。

如果仅想恢复**这 126 篇旧归档快照的搜索**，需另约停服维护窗口、先备份，再使用 `scripts.toggle_markdown_source` 的 `--enable` 模式并锁定该来源的 `--expected-documents 126`；随后运行 `scripts.build_embeddings` 补建待嵌入单元，审计索引后再启动服务。恢复搜索不会自动修复旧文件路径，App 中编辑这些来源文档仍会因找不到源文件而拒绝写回。若要与现在的 Obsidian 目录建立持续同步，应先单独设计身份映射、增删预览和冲突处理。
